# Phase 5: Scenario Analysis

Load this file only after the user approves the phase 1 research brief and asks to continue.

Do not use this file during phase 1.

## Goal

Explore plausible future paths from the approved research framing.

This phase is about structured alternatives, not a single-point forecast.

## Preconditions

Only proceed if the user already approved:

- a clear research question
- explicit boundaries
- a usable framework
- an evidence base
- a pressure-tested working view or at least a clear set of key uncertainties

If the major uncertainties are still unclear, return to phase 4 or earlier work instead of building shallow scenarios.

## What This Phase Should Produce

Produce a scenario set that makes future paths comparable:

- what the baseline path looks like
- what upside and downside paths look like
- what extreme or non-consensus path matters enough to consider
- what triggers would move reality from one path to another
- what first-order, second-order, and third-order effects each path would create
- what indicators would show which path is unfolding

Do not collapse the scenario set into one final prediction unless the user explicitly asks for that later.

## Workflow

Run these steps in order:

1. Restate the approved research question.
2. Restate the current working view and the key uncertainties that still matter.
3. Choose 3 scenarios that are genuinely distinct. A strong default set is:
   - `Baseline`
   - `Upside` or `Optimistic`
   - `Downside` or `Adverse`
4. Add a fourth scenario only when a true non-consensus or tail-risk path matters:
   - `Black Swan`
   - `Regime Shift`
   - `Non-Consensus Path`
5. For each scenario, define:
   - the core narrative in one or two lines
   - the trigger conditions
   - the key variables
   - what changes in the system
   - who benefits and who loses
6. For each scenario, analyze:
   - first-order effects
   - second-order effects
   - third-order or systemic effects
7. Identify what evidence or indicators would signal that the scenario is becoming more likely.
8. Compare the scenarios on probability, impact, and decision relevance if the user needs that framing.
9. Stop and wait for user confirmation before moving into final synthesis or recommendations.

## Output Shape

Use this compact backbone:

- `Approved Research Question`
- `Current Working View`
- `Key Uncertainties`
- `Scenario Set`
- `Triggers And Indicators`
- `System Effects`
- `Stop / Continue`

Add these sections only when useful:

- `Baseline`
- `Upside`
- `Downside`
- `Black Swan / Non-Consensus`
- `Who Wins / Who Loses`
- `Most Decision-Relevant Scenario`

## Scenario Standards

Each scenario should be meaningfully different.

Good scenario work:

- changes the logic of the system, not just the magnitude
- has explicit trigger conditions
- identifies what would be observed if it were unfolding
- surfaces higher-order effects, not just direct effects

Weak scenario work:

- uses three versions of the same story
- swaps labels like optimistic and pessimistic without changing mechanisms
- ignores triggers
- stops at first-order effects

## Quality Bar

The value of this phase comes from structured divergence.

Prefer:

- a small number of well-separated scenarios
- explicit uncertainty drivers
- observable triggers and indicators
- second-order and third-order effects where they matter

Avoid:

- pretending one path is certain
- collapsing scenario work into a final conclusion too early
- using generic best case / worst case language with no mechanism
- generating a long list of tiny variations

## Stop Rule

After producing the scenario set, stop.

Do not automatically proceed into:

- final synthesis
- final recommendation
- implementation planning

Allow at most a one-line next step, such as:

`Next step: synthesize which scenario is most decision-relevant and why.`
